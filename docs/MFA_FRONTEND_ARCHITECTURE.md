# SecretVault Multi-Factor Authentication (MFA) Frontend Architecture

## 1. Overview & Information Architecture
SecretVault's MFA frontend delivers an intuitive, secure, and resilient multi-factor authentication user experience integrated directly into the core authentication and settings flows.

MFA is structured as an individual account-security control positioned within the Account & Security settings hierarchy:
```
Settings
  └── Account & Security (Profile)
        ├── Personal Identity & Email
        ├── Password Management
        └── Multi-Factor Authentication (TOTP Authenticator + Single-Use Recovery Codes)
```

MFA configuration is deliberately decoupled from Workspace and Project settings to maintain clear boundaries between personal authentication security and organizational governance.

---

## 2. Core Security Invariants & Storage Prohibitions

> [!IMPORTANT]
> **Zero Persistent Storage of Sensitive MFA Material**: TOTP secrets, provisioning URIs, QR code data, unhashed recovery codes, and in-flight MFA challenge identifiers are **strictly prohibited** from browser persistent storage (`localStorage`, `sessionStorage`, `IndexedDB`, cookies) and URL parameters.

| Sensitive Artifact | Allowed State Lifetime | Storage Mechanism | Prohibited Locations |
| :--- | :--- | :--- | :--- |
| **TOTP Secret** | Transient during enrollment modal only | React Component State (`useState`) | `localStorage`, `sessionStorage`, cookies, Redux/persistent store, URLs, console logs |
| **Provisioning URI** | Transient during QR scan step only | React Component State (`useState`) | `localStorage`, `sessionStorage`, telemetry, error payloads, URL query params |
| **Recovery Codes** | Transient single-view display upon activation | React Component State (`useState`) | Persistent storage, backend read endpoints, URLs, analytics |
| **MFA Challenge ID** | In-flight pre-auth login flow only | React Auth State (`mfaChallengeId`) | `localStorage`, query strings, URL route paths, logs |
| **OTP / Passwords** | Input field during form submission | Component Memory | Persistent storage, error reporters, client logs |

## 3. Component Architecture & User Experience

### 3.1 Account Security View (`AccountSecurityView.jsx`)
- **Status Endpoint**: Queries `GET /api/v1/auth/mfa/status` on load using the authenticated API client.
- **Safe Metadata Display**:
  - `enabled`: Boolean status indicator with visual badge (`● Enabled` or `○ Disabled`).
  - `enrolledAt` & `verifiedAt`: ISO timestamp formatted to locale string.
  - `lastUsedAt`: Timestamp of the most recent successful second-factor validation.
  - `remainingRecoveryCodes`: Real-time count of available unconsumed recovery codes (e.g. `10 / 10 available`).
- **Interactive Triggers**:
  - Disabled state: `Enable MFA` button opens `MfaEnrollmentModal`.
  - Enabled state: `View Details` opens `MfaSecurityDetailsModal`, and `Disable MFA` opens `MfaDisableModal`.

---

### 3.2 MFA Enrollment Experience (`MfaEnrollmentModal.jsx`)
Multi-step modal workflow designed for maximum clarity and security guidance:

1. **Step 1: Overview & Prerequisites**
   - Explains TOTP authenticator requirements (Google Authenticator, Microsoft Authenticator, 1Password, Bitwarden, etc.).
   - Outlines the 4-step setup process.
2. **Step 2: Authenticator QR Code & Manual Secret Key**
   - Fetches provisioning parameters via `POST /api/v1/auth/mfa/enroll`.
   - Generates the QR code client-side using `qrcode.react` SVG rendering directly from `provisioningUri`.
   - **Manual Key Fallback**:
     - Masked by default (`•••• •••• •••• ••••`).
     - "Show setup key" toggle reveals key with a clear warning: *"Keep this key private. Anyone with it can generate MFA codes."*
     - Quick "Copy Key" button with temporary visual feedback.
3. **Step 3: Verification & Activation**
   - User enters the 6-digit TOTP code generated by their app.
   - Dispatches `POST /api/v1/auth/mfa/activate` with `{ code: "123456" }`.
   - Handles invalid codes, clock drift, or rate-limiting with user-safe error messages.
4. **Step 4: Single-View Recovery Codes & Mandatory Acknowledgement Gate**
   - Backend returns 10 single-use plaintext recovery codes.
   - **Export Options**:
     - "Copy All Codes" to clipboard.
     - Individual code copy button.
     - "Download Codes (.txt)" client-side generator creating `SecretVault-Recovery-Codes.txt`.
   - **Strict Acknowledgement Gate**: The modal completion button ("Complete MFA Setup") remains disabled until the user explicitly checks:
     `[x] I have safely saved my recovery codes. I understand they will never be shown again.`
   - Closing the modal clears all secrets and recovery codes from memory immediately.

### 3.3 Pre-Authentication Login Challenge (`MfaChallengeScreen.jsx`)
Integrated into the core login authentication state machine:

```
                  ┌───────────────────────────────┐
                  │    User Submits Email & Pwd   │
                  └──────────────┬────────────────┘
                                 │
                   POST /api/v1/auth/login
                                 │
                 ┌───────────────┴───────────────┐
                 │                               │
        MFA Disabled:                    MFA Enabled:
        HTTP 200 (Tokens)                HTTP 200 (MFA Required)
                 │                               │
                 ▼                               ▼
         Dashboard Entry            MfaChallengeScreen Active
                                    (mfaChallengeId in Memory)
                                                 │
                                 ┌───────────────┴───────────────┐
                                 │                               │
                         TOTP Verification:              Recovery Code:
                         POST .../verify-totp            POST .../verify-recovery
                                 │                               │
                                 └───────────────┬───────────────┘
                                                 │
                                                 ▼
                                        HTTP 200 (Tokens)
                                                 │
                                                 ▼
                                          Dashboard Entry
```

- **TOTP Mode**: 6-digit PIN input with automatic focus, numeric filtering, and clipboard paste support.
- **Recovery Mode Switch**: Single-click toggle to enter an alphanumeric single-use recovery code (`XXXX-XXXX-XXXX`).
- **Challenge Lifetime & Expiration Handling**:
  - `MFA_CHALLENGE_EXPIRED` (401): Displays *"Your verification session has expired. Please sign in again."* with a direct button to return to login.
  - `MFA_CHALLENGE_LOCKED` (403): Displays *"Too many failed attempts. This challenge has been locked for security."* and invalidates transient state.
  - `RATE_LIMIT_EXCEEDED` (429): Displays *"Too many verification attempts. Please wait before retrying."*

---

### 3.4 Step-Up MFA Disable Flow (`MfaDisableModal.jsx`)
Reflects backend step-up requirements:
- **Two-Factor Re-authentication**: Requires the user's current account password **AND** a valid TOTP code or unused recovery code.
- **API Dispatch**: `POST /api/v1/auth/mfa/disable` with payload:
  ```json
  {
    "password": "currentPassword",
    "totpCode": "123456" // or "recoveryCode": "1111-2222-3333"
  }
  ```
- **Post-Action**: Refreshes status from server, resets local state, and provides clear confirmation that MFA has been deactivated.

## 4. API Client Contracts & Endpoints

All MFA API calls use the centralized `apiClient` (`frontend/src/api/auth.js`) with automatic header injection, bearer token attachment, and unified error mapping.

| Endpoint | Method | Request Payload | Response Data |
| :--- | :--- | :--- | :--- |
| `/api/v1/auth/mfa/status` | `GET` | *None* | `{ enabled, status, enrolledAt, verifiedAt, lastUsedAt, remainingRecoveryCodes }` |
| `/api/v1/auth/mfa/enroll` | `POST` | *None* | `{ status, secret, provisioningUri }` |
| `/api/v1/auth/mfa/activate` | `POST` | `{ "code": "123456" }` | `{ status, recoveryCodes: [...] }` |
| `/api/v1/auth/mfa/verify-totp` | `POST` | `{ "challengeId": "...", "code": "123456" }` | `{ accessToken, refreshToken, tokenType, expiresIn, user }` |
| `/api/v1/auth/mfa/verify-recovery` | `POST` | `{ "challengeId": "...", "recoveryCode": "..." }` | `{ accessToken, refreshToken, tokenType, expiresIn, user }` |
| `/api/v1/auth/mfa/disable` | `POST` | `{ "password": "...", "totpCode": "..." }` | `{ status: "DISABLED" }` |

## 5. Logging & Telemetry Policies

- **Strict No-Log Policy**: Client-side logger and error reporters are audited to ensure OTP values, recovery codes, TOTP secrets, and challenge IDs are never written to `console.log`, `console.error`, or remote telemetry.
- **Sanitized Errors**: Error handling surfaces high-level user friendly guidance without logging backend exception classes, SQL/Redis traces, or sensitive request payloads.

---

## 6. Accessibility & Responsive Design

- **Accessibility (a11y)**:
  - Form controls include explicit labels, `aria-describedby` error bindings, and autocomplete annotations (`one-time-code`, `current-password`).
  - Modal dialogues maintain focus traps and Esc-key dismissibility (with confirmation warnings where appropriate).
  - High-contrast visual indicators accompany all state transitions (`● Enabled`, `✓ Verified`, `⚠ Warning`).
- **Responsive Layout**:
  - Dynamic layouts optimized for mobile, tablet, and desktop viewports.
  - Seamless mobile UX allowing users to switch between SecretVault and external authenticator apps without losing form state or triggering layout shift.
