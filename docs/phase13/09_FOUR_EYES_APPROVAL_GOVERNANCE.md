# Four-Eyes Approval Governance for Automation Actions

## 1. Overview

High-blast-radius automated actions (such as revoking production leases, disabling active application consumers, or destroying machine identities) can be guarded by a **Four-Eyes Approval Workflow**.

When `approvalRequired: true` is configured on an automation policy:
1. Matching events trigger condition evaluation.
2. Rather than executing side effects directly, an `AutomationApproval` entity is created in `PENDING` state.
3. Notifications are dispatched to authorized workspace security officers.
4. The action is held in queue until approved, rejected, or expired.

## 2. Table Schema (`automation_approvals`)

```sql
CREATE TABLE automation_approvals (
    id UUID PRIMARY KEY,
    workspace_id UUID NOT NULL,
    execution_id UUID NOT NULL,
    policy_id UUID NOT NULL,
    action_type VARCHAR(50) NOT NULL,
    action_payload_json TEXT NOT NULL,
    status VARCHAR(30) NOT NULL DEFAULT 'PENDING',
    requested_by UUID,
    decided_by UUID,
    rejection_reason TEXT,
    expires_at TIMESTAMP WITH TIME ZONE,
    decided_at TIMESTAMP WITH TIME ZONE,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

## 3. Anti-Self-Approval & Security Rules

1. **Anti-Self-Approval:** The user who authored or updated the policy cannot approve actions generated by that policy.
2. **TTL Expiration:** Approvals expire after a configurable duration (default 2 hours). Expired approvals transition to `EXPIRED` and cannot be re-opened.
3. **Audit Trail:** Decision events (`AUTOMATION_ACTION_APPROVED`, `AUTOMATION_ACTION_REJECTED`) are recorded in the immutable audit log with actor ID, IP address, and decision justification notes.
